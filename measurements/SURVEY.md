# Terminal survey

A plan for measuring a much larger corpus of grapheme clusters across every terminal and
multiplexer on this machine. Not part of the specs: this is a manual procedure, run by hand on
macOS with someone at the console, and its output is a set of committed measurements plus whatever
table corrections they force.

The four runs so far covered 67 clusters. Growing the set from 44 to 67 cost the counting model two
departures and the width tables five entries, so the rate of discovery has not fallen off yet. This
is the cheapest way to find the rest.

## What is measured, and at what scale

Two instruments, and they do not belong at the same scale.

| | counted width | advance and drawn width |
|---|---|---|
| how | `CPR` after each cluster | photograph the screen |
| needs a console | no | yes |
| needs the screen unlocked | no | yes |
| needs screen recording permission | no | yes, per app |
| font dependent | no, proved over three fonts | yes |
| soft readings | none, it is an integer from the terminal | 8 to 12 of 67 |
| corpus | the whole thing | a curated subset |

Counted width is what keeps the cursor in step with the terminal, it is the number the shard has to
predict, and it costs two escape sequences per cluster. That is the survey. Advance and drawn width
are a separate, much smaller exercise at the end.

A multiplexer has no glyphs of its own — `tmux` and `screen` render through whichever terminal they
are attached to — so photographing one measures the host's font and says nothing about the
multiplexer. **Only the counted width is meaningful under a multiplexer**, and the photographic
phase skips them.

## The matrix

Four hosts, four layers, sixteen combinations for counted width:

| host | version | bare | `tmux` | `screen` 4 | `screen` 5 |
|---|---|---|---|---|---|
| Terminal.app | 2.15 (build 470.2) | yes | yes | yes | yes |
| Ghostty | 1.3.2 | yes | yes | yes | yes |
| iTerm2 | 3.6.11 | yes | yes | yes | yes |
| kitty | 0.48.2 | yes | yes | yes | yes |

The multiplexers are the interesting half. Each does its own width accounting and sits between the
application and the terminal, so each can introduce the fault the host does not have or mask the one
it does.

Both `screen` builds are tested and they are twenty years apart, which makes the pair worth more
than either alone: any difference between them is `screen` changing its mind rather than a terminal
disagreeing.

| multiplexer | version | path |
|---|---|---|
| `tmux` | 3.7c | `/opt/homebrew/bin/tmux` |
| `screen` (Apple) | 4.00.03, dated 2006 | `/usr/bin/screen` |
| `screen` (GNU) | 5.0.2, built 2026-07-11 | `/opt/homebrew/bin/screen` |

Label the old one as Apple's build rather than as GNU `screen` generally, and expect width tables
from its era.

### The grapheme-mode axis

kitty and Ghostty implement mode 2027, which changes whether the terminal counts clusters or code
points — exactly the thing under test. Where `DECRPM` reports the mode as supported, run that host
twice, once with 2027 on and once off, and record which. That makes six host runs rather than four
for the bare phase. Terminal.app and iTerm2 do not implement it; iTerm2 has its own Unicode version
setting (8 or 9) that moves widths instead, so **record iTerm2's setting and do not assume it**.

## The corpus

Generated by a committed script so every environment measures an identical list and runs taken
weeks apart stay comparable. Target 5,000 to 10,000 clusters.

* Every fully-qualified sequence in `emoji-test.txt`, roughly 5,000. This file is not currently
  fetched; add it to `SOURCES` in `scripts/gen_unicode.cr`.
* One representative per combination of East Asian Width class, grapheme break class, `Emoji`,
  `Extended_Pictographic` and Indic conjunct class. This is where an unmeasured corner is most
  likely to be hiding, because it is chosen by the property table rather than by taste.
* Every RGI subdivision flag, since the tag sequence was one of the three that broke the counting
  model.
* Conjuncts across every script with a virama: devanagari, bengali, gurmukhi, gujarati, oriya,
  tamil, telugu, kannada, malayalam, sinhala, khmer, myanmar. Three of the five width corrections
  were conjuncts, and all three were the same shape.
* Jamo in every arrangement: `L`, `LV`, `LVT`, `L+V`, `L+V+T`, and a `V` or `T` with no lead, which
  is the case the current rule guesses at rather than knows.
* Regional indicator runs of one to five.
* Variation selectors on bases that are emoji, bases that are pictographic and not emoji, and bases
  that are neither.
* Combining mark stacks of one, two and four; enclosing marks; keycaps with and without a selector.
* The existing 67 unchanged, as a control. If they do not reproduce, the harness is wrong.

Excluded: anything containing a control character, `CR`, `LF`, or `ESC`, and any cluster whose
predicted width exceeds the row.

Write it to `measurements/corpus.tsv` and commit it. `scripts/measure_columns.cr` grows an optional
argument naming a corpus file, falling back to `scripts/glyph_samples.cr` as now.

### The corpus as built

`scripts/gen_corpus.cr` produces 5,274 clusters, 362 KB, from Unicode 16.0.0.

| group | clusters | tell the two models apart |
|---|---|---|
| `emoji-fully-qualified` | 3,761 | 2,312 |
| `emoji-minimally-qualified` | 1,009 | 1,009 |
| `emoji-unqualified` | 239 | 35 |
| `property` | 83 | 5 |
| `control` (the original 67) | 67 | 26 |
| `conjunct` | 36 | 6 |
| `enclosing` | 35 | 23 |
| `presentation` | 25 | 3 |
| `emoji-component` | 9 | 0 |
| `jamo` | 6 | 2 |
| `regional` | 4 | 2 |
| **total** | **5,274** | **3,423** |

Three thousand four hundred clusters where our cluster width and our per-code-point count disagree
is what makes this worth running: each one is a place a terminal can come down on a side. The
minimally-qualified emoji are the richest seam — all 1,009 of them differ, because that is what
missing a variation selector does.

Two properties of the corpus to know before reading any result from it.

* **Nineteen clusters our own segmenter splits into two or three.** Some are correct — a letter,
  a joiner and a letter is two clusters under GB11, and three regional indicators is two under
  GB12. Others are the Indic conjunct rule not reaching every script: `InCB` does not cover
  gurmukhi or tamil, so their virama sequences come apart. They stay in, since a cluster we split
  and the terminal does not is worth knowing about.
* **Only four tag sequences exist**, because Unicode defines only three RGI subdivision flags.
  That corner is as covered as it can be.

## Protocol

Per cluster the current instrument does home, erase line, `CPR`, write, `CPR` — two round trips.
At 10,000 clusters that is 20,000 replies, so the round trips have to be amortised.

* **Batch.** Write 100 samples with their position reports in one flush, then read 200 replies.
  This is what `WidthProbe` already does for its seven.
* **Resynchronise on a short batch.** A dropped reply desynchronises everything after it, so a batch
  that returns fewer replies than expected is discarded and re-run one cluster at a time. Never
  interpret a short batch positionally.
* **Autowrap off** (`DECAWM`), so a cluster the terminal counts generously cannot wrap and take the
  next reading with it. Each sample still starts at column 1 of its own row.
* **Abort loudly** if the first batch draws no reply at all. A terminal that does not answer `CPR`
  cannot be surveyed, and a run of 10,000 empty readings should not look like data.
* **Record the environment**: terminal and version, `TERM`, `TERM_PROGRAM`, multiplexer and version,
  mode 2027 state, iTerm2 Unicode version, font and size, window size. Font does not affect this
  measurement, but recording it is what proved that.

Expect roughly a minute per environment once batched, so the sixteen counted-width runs are about
twenty-five minutes including launch overhead.

## Launching each environment

The mechanics are where the previous runs lost the most time. Each recipe below creates its own
window and never types into one it did not create.

### Terminal.app

`osascript`, `do script ""` for a new window, set `font name`, `font size`, `number of columns` and
`number of rows` on that tab, then `do script "…" in win`. Proven; `scripts/terminal-run.sh` in the
scratchpad already does it. It is the only one of the four that will report its window bounds, which
is what lets the photographic phase capture the window rather than the screen.

### Ghostty

`open -na /Applications/Ghostty.app --args --config-default-files=false --config-file=<throwaway>`.
The config must set `initial-command` (not `command`, which runs in every surface — that opened
seventeen windows at once) and `window-save-state = never` (which is what restored those seventeen).
Do not use `-e`: arguments from another application raise an "Allow Ghostty to execute" dialog that
nothing can answer unattended.

### iTerm2

`osascript`, `tell application "iTerm" to create window with default profile`, then `write text` to
the session. Needs Automation approval the first time. Create a throwaway profile rather than using
the default if the run should not inherit the user's font and Unicode settings.

### kitty

Launchable from the command line directly, unlike the others:

```bash
/Applications/kitty.app/Contents/MacOS/kitty --config NONE \
  -o font_family="SF Mono" -o font_size=11 \
  sh -c '<instrument> <corpus> <output>'
```

`--config NONE` is the isolation switch. `kitten @` remote control is available if driving an
existing instance turns out to be easier than launching one.

### tmux

Runs inside a host terminal, attached, since `CPR` has to reach a real terminal and come back. Use a
private socket and no config so the user's server and sessions are untouchable:

```bash
tmux -L termbuf -f /dev/null new-session -- <instrument> <corpus> <output>
```

### GNU screen

Same shape, its own session name, and no config:

```bash
/usr/bin/screen        -c /dev/null -S termbuf-survey <instrument> <corpus> <output>
/opt/homebrew/bin/screen -c /dev/null -S termbuf-survey <instrument> <corpus> <output>
```

Apple's build is old enough that it may mangle or swallow sequences the others pass through. If it
does, record that as the result rather than working around it.

## Permissions

All of these need someone at the console, once each, and a **process started after the grant** —
permissions are read at launch, so an instance running beforehand will not have them.

* Automation, for the driving process to control Terminal.app and iTerm2 by AppleScript.
* Screen Recording, per application, for the photographic phase only: Terminal.app, Ghostty, iTerm2,
  kitty. Ghostty's grant is what the locked-screen run appeared to be missing and was not.
* The screen must be **unlocked** for the photographic phase. A locked screen composites nothing and
  `screencapture` returns the wallpaper on every page, which looks like a permission failure and is
  not. Check `ioreg -n Root -d1 -a | grep CGSSessionScreenIsLocked` before starting.

The counted-width survey needs none of this and runs with the screen locked.

## Output and analysis

One directory per environment, `measurements/<host>-<version>[-<layer>]/`, holding `counted.tsv`
with the cluster, the terminal's answer, and both model predictions, plus a `README.md` recording
the environment as above.

The analysis asks three questions.

1. **Which environments carry `Quirk::PerCodePointColumns`?** The discriminator is one cluster:
   four joined faces answering 11 rather than 2. The probe already sends it, and as of `b0cb5c2` the
   shard decides the quirk from that answer, so this both tests the detection and populates the
   `QUIRK_PATTERNS` fallback list for terminals that stay silent.
2. **Where does the model disagree, and does anything else agree with it?** The criterion that
   worked: a cluster where **two or more independent implementations agree with each other and
   against us** is a table bug, not a terminal quirk. One terminal alone disagreeing is a quirk
   candidate and needs a second opinion before anything in `src/` moves.
3. **What is the residual?** Clusters no model predicts anywhere, the count of what is still
   unexplained, which belongs in the notes rather than in a table.

## Phases

Ordered so a failure wastes as little as possible.

1. **Build and validate the corpus offline.** Generate it, check nothing contains a control
   character, score it against the current model. No terminal involved.
2. **Dry run.** The existing 67 clusters through all sixteen combinations. Every environment must
   reproduce the numbers already committed for Terminal.app and Ghostty, and the harness must
   survive `screen`. Fix the harness here, where a mistake costs a minute.
3. **Full corpus, bare hosts**, including the mode 2027 variants.
4. **Full corpus under `tmux` and both `screen` builds.**
5. **Photographic phase.** The most interesting hundred or so clusters, bare hosts only, console
   required. Choose them from what phases 3 and 4 disagreed about, and carry the `edge` column so
   soft readings stay visible.
6. **Analysis and changes.** Table corrections where two implementations agree, new fixture entries
   in `spec/caps/quirk_spec.cr`, and a note for the residual.

## Rules of engagement

* **Ask before launching anything that takes the screen**, every time.
* **Never `killall`.** Record the PID of what was launched and signal only that. The user's own
  Ghostty and his terminals are not ours to close.
* **Private sockets and session names** for `tmux` and `screen`, with config files bypassed, so an
  existing session cannot be attached, resized or killed by accident.
* **Never type into a window this procedure did not create.**
* Throwaway profiles and configs everywhere, so no run depends on or alters the user's settings.

## What this would change in the shard

Nothing structural is expected. The likely outcomes are more entries in the width tables, more
departures in `Unicode.code_point_columns` if another terminal counts per code point differently,
possibly a second quirk if a multiplexer is wrong in a new way, and a longer fixture. If the counted
width turns out to be predictable across sixteen environments at ten thousand clusters, that is the
strongest statement this project can make about the one number it has to get right.
